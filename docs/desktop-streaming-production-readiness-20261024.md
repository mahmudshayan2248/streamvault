## First-frame investigation

The previously reported intermittent Chrome stall at media time 0.18 seconds did **not** reproduce in six isolated 20 Mbps Chrome replays. All six played about 15 media seconds without a playback stall; first-frame times were 7.67–7.69 seconds. An earlier controlled replay had stalled with `bufferSeekOverHole` and `bufferStalledError`; its cause remains unconfirmed.

Those six traces did establish a separate, deterministic startup defect. Every video rendition begins at PTS about 0.083 seconds while audio begins at zero. The browser's first buffered range was `[0.083333, 4.010666]`; the player waited for `currentTime === 0` to have three seconds ahead, which could never become true. `waitForPresentation` then returned after its six-second fallback. The repair moves the title-start playhead into a decoded buffered range only when its leading gap is at most 0.25 seconds. It does not skip larger gaps or seeks elsewhere. The frontend script URL was versioned so the repaired file can be fetched on rollout.

Three 20 Mbps Chrome replays after the repair reached first frame in **2.12, 1.92, and 1.72 seconds**, played about 15 media seconds, and recorded no stalls. The browser trace showed `MEDIA_ATTACHED`, `MANIFEST_PARSED`, the first `FRAG_BUFFERED`, `loadedmetadata`, `canplay`, a seek to 0.083333 seconds, and `playing`. One regression test covers the bounded gap and refuses to skip a 0.5-second gap. This is evidence for the startup-delay repair; it is not proof that the intermittent 0.18-second stall is eliminated.

A later, separate headless Chrome failure left `MediaSource` closed before any `MEDIA_ATTACHED` event; HLS parsed fragments but no SourceBuffer existed and preparation timed out at 120 seconds. The test profile had accumulated nine preview tabs because an exploratory trace script did not close its targets. After closing those tabs, ten serial adaptive starts and five paired adaptive starts played normally. Five additional paired single-rendition starts failed to attach while multiple test tabs were again left open. This identifies a browser-harness resource confound in those runs; the exact browser resource limit and the original 0.18-second stall remain unproven. Sustained results below use at most two tabs and inspect per-second media advancement in addition to the player's stall counter.

## Sustained synthetic network measurements

Cold four-rendition encoding was **21.7 seconds for 12 seconds of video** in the earlier benchmark and **19.79 seconds** in the later separate local run, with 205.3% and 255.7% peak FFmpeg CPU respectively. The different runs do not establish an encoding speedup, and neither sustained playback test re-encoded media: all scenarios served a completed package. The architecture's measurable gain here is cache reuse and lower delivered bitrate. Uncached on-demand four-rendition encoding remains slower than playback and is unsuitable as the weak-link serving path.

An isolated 600.025-second synthetic title was made by timestamp-continuous looping of the existing 60-second two-audio test pattern and pre-transcoded into four complete renditions. The package has 151 segments per rendition and occupies 510,252,809 bytes. Chrome CDP disabled HTTP cache, imposed 100 ms latency, and throttled download and upload. These tests are **simulated links**, not real mobile data or production Mac mini measurements. The looped fixture is one 600-second media file but does not represent varied real-title content.

## Mac mini capacity and deployment automation

The Mac mini is a 2-core/4-thread, approximately 8 GB machine. The prior read-only snapshot showed 3.74 GB free RAM and 67.02 GB free disk; `/api/playback/status` on this run still reported zero active workers. No isolated Mac mini load environment exists, so 1/2/3/5-viewer CPU, RAM, disk-read, concurrent-seek, and safe-capacity claims are **unmeasured**. Local MacBook cache-concurrency results cannot establish a Mac mini viewer limit. The adaptive cache enforces a private root, one FFmpeg child per root, bounded bytes/free-space reserve, active-reader holds, and eviction tests; Mac mini ACLs and limits still require staged verification.

For a bounded MacBook-only cached-delivery probe, 1, 2, 3, and 5 synthetic clients each fetched 12 indexed 360p segments from the already completed package. All 12/24/36/60 requests succeeded. Respectively, total elapsed times were 64.5/46.8/63.9/110.3 ms and p95 request times were 11.3/5.8/7.9/14.6 ms; the local cache status reported 948 asset hits, zero misses, and 250.32 MB served since the preview process started. This probes local HTTP cache delivery only, without full viewers, seeks, Mac mini CPU/RAM measurements, or storage pressure. It provides no defensible Mac mini concurrent-viewer limit.

## Regression and release procedure

The final `node --test` run passed all 10 adaptive HLS, passive capability, and PlayerSession recovery/startup tests, including the new bounded leading-gap regression. The 16 frontend playback-session tests, 17 audio-language tests, audio playback regression, and media modal UI also pass. `verify:hostinger` had an inherited stale assertion for 2026-09-12 JavaScript asset URLs even though the review base used 2026-10-23 URLs. Its exact URL assertion was updated for this release and the deployment verifier now passes (34 referenced assets, 26 active scripts, 65 channel logos). The broad suites were rerun and retain three inherited failures: `test:player-ui` expects a seek-row loading indicator, `test:runtime-handler-paths` cannot extract production `play`, and `test:hostinger` passes its boundary and runtime-resilience stages before service-worker caching fails to handle `/api/ready`. None of those test or implementation files changed in this repair. `test:playback` stops at the first inherited player-UI failure.

Before deployment, preserve the Mac mini launcher, environment, cache, `server.js`, and exact capability module; recheck process identity and the two hashes. Stage only the guarded capability module plus the two adaptive modules in an isolated directory, use a private bounded cache root, and pre-transcode an approved title during an operator-selected idle window. With separate approval, install the staged files with `SV_ADAPTIVE_HLS_ENABLED=0`, restart under observation, verify existing routes and direct playback, then enable a limited canary and run all real-media, Safari, sustained mobile-data, concurrent-viewer, and cleanup gates. Roll back by disabling the flag, restoring the saved exact module, restarting under observation, and verifying the original routes. The frontend can be rolled back to the preceding reviewed commit.
