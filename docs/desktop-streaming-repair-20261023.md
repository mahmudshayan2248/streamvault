# Desktop streaming repair: investigation and preview

This branch starts from `origin/hostinger-frontend-only` at `1f33c04888ef9235c9b882cee2b30779cdb348b9`. On 2026-10-23, the deployed `app-v3.js`, `player-session.js`, `player-vlc-v1.js`, and `player-runtime-v2.js` matched that branch byte for byte. The original `/Users/shayan/streamvault` checkout is dirty and was not changed.

The public backend returned a single `#EXT-X-STREAM-INF:BANDWIDTH=1887070` video variant for an existing HLS session. It offered no lower encoded bitrate. A Chrome preview of Extraction over an emulated 500 Kbps, 100 ms link advanced from 1407.5 to 1415.2 media seconds over about 40 wall seconds after an uncached seek. This is a simulated browser network, not a measurement of the user's mobile data. It demonstrates the single-variant stream cannot maintain real-time playback on that link; it does not isolate FTP, Tunnel, or Hostinger throughput. Read-only SSH to the Mac mini timed out, so deployed backend bytes and CPU headroom remain unverified.

The frontend change schedules at most three HLS network restarts per error burst with 500/1000/2000 ms backoff and up to 249 ms jitter. A successful fragment resets the burst. Close, seek, error, or source replacement invalidates pending retries. Retrying only loads data and never calls play, preserving pause intent. Normal low-buffer sampling no longer restarts an active HLS loader. HLS.js uses automatic startup selection with a 500 Kbps initial estimate and conservative bandwidth margins when a multi-variant master is eventually available. With the currently deployed single variant, these settings do not lower bitrate.

Local preview: `python3 -m http.server 8765 --bind 127.0.0.1 --directory hostinger` and open `http://127.0.0.1:8765/` in desktop Chrome. The preview serves this branch's actual frontend assets and uses the existing production backend configured in `runtime-config.js`; it is **not isolated from backend reads or media requests**. It does not modify production files. The browser test opened Extraction, observed advancing video with roughly 58 seconds buffered, then verified pause, resume, and forward seek. It did not prove long-run playback, Safari, mobile regression, series, audio/subtitle switching, or improvement under real mobile data.

Before any deployment, verify exact backend files and capacity on the Mac mini, prepare bounded persistent 1080p/720p/480p/360p encoded renditions for approved sources, and test the full playback matrix against a staging backend. The current GitHub `master` and PR #139 use a different `public/` player and routes; they are not production-compatible deployment bases. Deploy only after review and approval.
